## 4. 第三段：总体架构（3分钟）

### 建议配合的图

答辩时建议 PPT 上放 **两张图**：

**图1：系统分层架构图（展示全貌）**

```
┌─────────────────────────────┐
│  外部调用方（司机App）       │
└──────────┬──────────────────┘
           │ HTTP REST
┌──────────▼──────────────────┐
│  BFF网关层 (Gin)            │
│  bffDriver 进程              │
│  职责：HTTP处理 + 外部服务集成 │
└──────────┬──────────────────┘
           │ Kitex RPC (Thrift)
┌──────────▼──────────────────┐
│  微服务业务层 (Kitex)        │
│  srvDriver 进程              │
│  职责：核心业务逻辑           │
└─────┬──────────────┬────────┘
      │              │
┌─────▼────┐  ┌──────▼──────────┐
│ MySQL    │  │ MongoDB (位置)   │
│ 26张业务表│  │ 2dsphere地理索引 │
└──────────┘  └─────────────────┘
┌────────────────────────────────┐
│ Redis (缓存/抢单池/对话上下文)  │
└────────────────────────────────┘

外部依赖：高德地图API / DeepSeek AI / 百度TTS
```

**图2：进程与通信关系（展示技术栈）**

```
进程A: bffDriver (Gin HTTP)
  ├── 17个API路由
  ├── RPC客户端 → 调进程B
  └── HTTP客户端 → 调高德/DeepSeek

进程B: srvDriver (Kitex RPC)
  ├── 25个RPC方法
  ├── 5个Service模块
  ├── GORM → MySQL
  └── go-redis → Redis
```

### 讲解话术模板

> 从架构上看，系统分为两层，运行两个独立的 Go 进程：
>
> **上面是 BFF 网关层**，用 Gin 框架处理司机 App 发来的 HTTP 请求。这一层主要负责三件事：一是把 HTTP 转为内部 RPC 调用；二是聚合外部服务，比如调用高德地图查天气、调用 DeepSeek 做 AI 对话；三是对外屏蔽内部服务细节。
>
> **下面是微服务业务层**，用 Kitex 框架提供 RPC 服务，所有核心业务逻辑都在这一层——派单引擎、司机上下线状态机、抢单池、订单管理。
>
> 两层之间通过 Thrift 协议通信，IDL 文件定义了 25 个 RPC 方法。数据层用了三种存储：MySQL 存业务数据、MongoDB 存司机实时位置（利用 2dsphere 索引做附近司机查询）、Redis 做抢单池缓存和 AI 对话上下文。

### 可能被追问

**Q：为什么不用 gRPC 而是 Kitex + Thrift？**

> 主要原因是技术栈选型。Kitex 是字节开源的 RPC 框架，基于 Netpoll 网络库，在小包高并发场景下性能优于 gRPC。Thrift 协议相比 Protobuf 更简洁，生成的代码可读性更好。而且团队对 Thrift 更熟悉。

**——不用过度解释技术细节，点到为止。**

**Q：BFF 层和服务层为什么要分开？合在一起行不行？**

> 分开的主要目的是职责分离。BFF 层处理 HTTP 协议转换和外部服务集成，服务层专注核心业务。这样两个进程可以独立部署、独立扩缩容。比如早晚高峰派单压力大，可以只扩容服务层，BFF 层保持不动。合在一起当然可以，但后期维护和扩展会受限。

### 注意事项

- **这一块最容易超时**，控制在3分钟内
- 不要逐行念代码目录结构
- 不要说"kitexGen是自动生成的代码"——展示你知道它是生成的就够了

## 5. 第四段：核心模块深挖（5分钟）

**建议只选 1-2 个模块深入讲，不要全讲。** 推荐选 **派单引擎** 或 **AI数字人**，选你最自信的那个。

### 方案A：讲派单引擎（推荐首选）

这是项目最复杂的模块，最能体现你的技术深度。

#### 讲解流程

```
1. 派单的入口
   └→ DispatchOrder 接口触发派单

2. 找附近司机
   └→ MongoDB $nearSphere 查询
   └→ 默认半径3公里,限制50个候选

3. 逐个过滤候选司机（这是核心）
   └→ C1: 必须是听单状态
   └→ C2: 距离在半径内
   └→ C3: 车型匹配
   └→ C4: 无进行中订单
   └→ C5: 未达日接单上限
   └→ C6: 服务分不低于阈值

4. CAS 抢占订单
   └→ UPDATE order SET status=1, driver_id=?
       WHERE order_id=? AND status=0
   └→ RowsAffected==0 说明被抢走，继续遍历下一个

5. 全部失败 → 进抢单池

6. 后续：司机拒绝 → retryDispatch → 再失败 → 进抢单池
```

#### 对应PPT上的图

建议画一张 **横跨3列的流程图**：

```
左侧（输入层）      中间（引擎层）          右侧（输出层）
MongoDB找附近司机 → 6个过滤条件 →         CAS抢占成功 → 返回成功
                  （画成6个判断框）       全部失败 → 进抢单池
```

#### 讲解话术模板

> 我重点讲一下派单引擎的设计。它是整个系统的核心，负责把乘客订单分配合适的司机。
>
> 当收到派单请求后，引擎先通过 MongoDB 的 $nearSphere 查询附近 3 公里内正在听单的司机，默认最多取 50 个候选。
>
> 然后逐个检查这 50 个候选司机，依次过滤——必须是听单中状态、服务分不低于 60、没有进行中的订单、没达到每日接单上限、距离在半径内、车型匹配。只要有一个不满足就跳过。
>
> 全部通过后，用一条 SQL 做 CAS 乐观锁抢占：
>
> `UPDATE order SET status=1, driver_id=? WHERE order_id=? AND status=0`
>
> 如果影响行数为 0，说明订单被别的司机抢走了，继续尝试下一个候选。如果所有候选都失败，订单自动进入抢单池，等待司机主动抢单。
>
> 这种设计保证了高并发下的数据一致性，而且不需要加锁。

#### 可能被追问

**Q：MongoDB 查附近司机性能怎么样？怎么保证实时性？**

> MongoDB 的 2dsphere 索引对地理空间查询做了优化，单次查询一般在 5ms 以内。实时性方面，每 3-5 秒上报一次位置，5 分钟内没有更新的位置会被视为过期，不再纳入候选。

**Q：50 个候选司机不够怎么办？**

> 实际场景中，在一线城市核心区域，3 公里内可能远超 50 个司机。目前的策略是先取 50 个，如果这 50 个都不符合条件，再进行扩展半径搜索。配置里的 `expanded_radius_km` 和 `max_expanded_attempts` 就是做这个用的。

**Q：为什么不用 Redis GEO 直接做附近查询？**

> Redis GEO 查距离确实快，但做空间范围查询不如 MongoDB 灵活。而且 MongoDB 可以同时返回司机的状态、更新时间等额外字段，Redis 需要多次查询才能拼出完整信息。加上这个项目本来就在用 MongoDB，没有额外运维成本。

#### 如果老师让你"用一句话讲清楚派单"

> **先找附近司机，再按6个条件过滤，符合条件的用CAS乐观锁抢单，抢不到就换下一个，全都不行就进抢单池。**

### 方案B：讲AI数字人助手

如果觉得派单引擎太复杂，或者老师对AI更感兴趣，选这个。

#### 讲解流程

```
1. 三层递进式意图匹配
   ├── 第一层：精确匹配（正则命中→say/call_api）
   ├── 第二层：上下文推演（基于上一轮意图）
   └── 第三层：LLM兜底（DeepSeek API）

2. 意图匹配的三种动作
   ├── say: 直接回复固定话术（"你好呀！我是花小猪助手"）
   ├── call_api: 调业务API拿真实数据（查今日收入、查余额）
   └── llm_chat: 走DeepSeek LLM处理（闲聊、复杂查询）

3. 成本控制策略
   ├── 高频操作精确匹配（0成本）
   ├── 数据查询调API拿真实数据（精确+低延迟）
   └── 仅复杂场景才走LLM（控制API调用量）

4. 防LLM幻觉
   ├── 数据直给（程序拼接"今天接了5单"）
   ├── system prompt严格限制
   └── 兜底话术"暂时查不到"
```

#### 讲解话术模板

> AI 数字人助手的核心设计理念是"用最经济的方式做最准确的事"。
>
> 系统采用三层递进式处理：用户输入首先走精确意图匹配，如果命中"出车""查余额"这些操作，直接调业务 API 返回真实数据；如果没匹配到，尝试基于上一轮对话做上下文推演；最后才走 DeepSeek LLM 兜底。
>
> 这样设计的目的是控制成本——高频业务操作走精确匹配几乎零成本，只有闲聊才调 LLM API。同时也防止了 LLM 编造数据——所有数据查询类操作都是先调接口拿到真实数据，LLM 只负责润色表达。

#### 可能被追问

**Q：意图匹配的正则规则那么多，怎么维护的？**

> 所有意图规则都配置在 digital_human.yaml 文件里，不需要改 Go 代码。产品运营可以直接修改 YAML 文件来调整触发词、回复话术，甚至新增意图。正则支持字符串包含和完整正则两种模式，用 `^` 或 `$` 开头结尾的就是正则，否则是字符串模糊匹配。

**Q：如果 DeepSeek API 挂了怎么办？**

> 如果 LLM API 不可用，系统会自动降级到"纯意图匹配"模式。常见操作（出车、查单、查余额）不受影响，只是闲聊类问题会回复"这个我暂时查不到，您说点别的吧"。Redis 如果也不可用，AI 助手仍然能正常工作，只是不能保留对话上下文。

## 6. 第五段：项目亮点与难点（3分钟）

### 怎么选

从下面的列表里 **挑2-3个你觉得最自信的讲**，不要全讲。

### 推荐组合（最安全）

> **① 双通道派单设计 + ② CAS并发控制 + ③ 优雅降级**

### 讲解话术

| 亮点 | 一句话概括 |
|------|-----------|
| **双通道派单** | 系统智能派单 + 抢单池双通道互补，派单失败的订单自动进池，司机的选择权也更大 |
| **CAS乐观锁** | 所有并发竞争场景都通过 Compare-And-Swap 实现，用一条SQL解决数据一致性问题 |
| **BFF + 微服务** | 两层架构隔离，BFF专注HTTP和外部服务集成，服务层专注核心业务 |
| **AI混合意图** | 精确匹配 + 上下文推演 + LLM兜底三层递进，兼顾成本、速度和准确性 |
| **优雅降级** | Redis/MongoDB/DeepSeek任一不可用时，系统不会崩溃，只是功能适当降级 |
| **配置驱动AI** | 数字人行为全在YAML配置中，修改无需重新编译部署 |

### 可能被追问

**Q：你刚才说的这些，有没有数据支撑？比如派单成功率多少？**

> （如果是毕设项目）目前项目处于开发阶段，还没有线上的真实生产数据。但从测试来看，派单引擎的候选筛选平均耗时在 10ms 以内，CAS 并发控制在压力测试下没有出现超卖。

**——诚实回答，不要编数据。**

**Q：这些"亮点"是你自己设计的还是参考了别人的方案？**

> 整体架构参考了业界常见的微服务设计模式。派单引擎中的CAS乐观锁抢占、MongoDB地理空间查询找附近司机这些方案在网约车行业中是比较成熟的做法。AI的混合意图匹配是我自己设计的，在控制成本的同时保证准确率。

**——既要展示你了解行业实践，也要说明自己的贡献。**

## 10. 常见"送命题"应答策略

### Q：你觉得这个项目有什么不足之处？

> （主动说出来比你被问到强，建议在总结时主动提）
>
> 主要有三点：一是目前没有接入服务注册中心，BFF 直连服务层，不适合生产环境；二是监控和日志还不够完善，只有基础日志输出；三是没有做读写分离，高并发下 MySQL 可能成为瓶颈。

### Q：这个项目是你一个人做的吗？每个部分你都参与了吗？

> 项目由我独立设计并实现。从技术选型、架构设计到编码实现都是我自己完成的。在派单引擎设计时参考了网约车行业的一些实践方案。

**——诚实回答，如果你参考了开源代码或文档，大方承认。**

### Q：这个代码量看起来不是很大，你觉得工作量够吗？

> 代码行数约2000行左右，但实质性的设计工作包括：Thrift IDL 的定义和 25 个 RPC 方法的设计、派单引擎的过滤策略和 CAS 并发控制方案、AI 三层意图路由架构、MongoDB 地理空间查询方案等。代码量不等于工作量，设计决策和方案选型花费的时间更多。

**——强调设计工作，不要陷入"代码行数"的争论。**

### Q：你这个如果上线了，最大的风险是什么？

> 最大的风险有两点：一是高并发下 CAS 乐观锁虽然保证了一致性，但如果冲突率高，会导致大量重试和派单延迟；二是 MongoDB 如果出现故障，派单引擎会直接降级，影响整个系统的订单应答能力。这两个问题的改进方向是引入 Redis 做缓冲层和 MongoDB 做副本集群。

### Q：这个问题我不会回答怎么办？

> （千万不要沉默或瞎编）
>
> "这个问题我确实没有深入考虑过，我的理解是...（说你知道的部分）。具体的细节我下来再查一下，您看可以吗？"

**——大方承认，不要编。老师更讨厌瞎编而不是说不知道。你也可以把问题引向你知道的方向。**

### Q：你和别人的项目比起来，有什么不一样的？

> 主要区别在于 AI 数字人助手的集成。很多网约车系统没有这个设计，我设计的 AI 助手通过"精确匹配 + 上下文推演 + LLM 兜底"三层架构，在控制成本的同时实现了用自然语言操作业务功能的能力。这是与同类项目相比最大的差异化亮点。
